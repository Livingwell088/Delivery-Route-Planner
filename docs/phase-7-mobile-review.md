# Phase 7 Step 3: mobile address review

Implemented 2026-10-16. Step 2 is committed as `205c651`; Step 3 as `fbf2f51`.
The migration limitations below describe Step 3. [Step 4](phase-7-confirmed-locations.md)
adds backend confirmation and persistence. The required Expo SDK 57 documentation and `mobile/AGENTS.md` were
read before mobile code changes. No new dependency or Google key was added to
the mobile app; existing receipt OCR and correction rules remain intact.

## User flow

Opening confirmation after OCR, manual recovery, or a mock receipt starts a
backend address lookup after a 700 ms pause. Pausing on subsequent address edits
also triggers a lookup, so each completed lookup consumes Google usage. This
step introduces no cache, request retry loop, or spending cutoff. Order number
or time edits do not trigger another address lookup.

The screen shows checking/error/correction states, full candidate addresses and
their town/state/ZIP, warnings, preserved unit information, and Google Maps
attribution. There is no new address map or native dependency. The selected
location is visible on the existing order map after confirmation.

- A single usable result without review flags is preselected, but the driver
  still compares it to the receipt and uses the existing final confirmation.
- Several usable candidates or a review-required single result require an
  explicit candidate choice. Warnings stay visible after choosing.
- Imprecise hints cannot be selected. Invalid, unavailable, loading, stale, or
  unselected results block saving in both the UI and save handler.
- A destination edit clears coordinates and provider metadata immediately.
  Request cancellation plus generation checks prevent old successes or errors
  from replacing a newer result, including a transport that ignores abort.
- Cancel, rescan, or navigating away cancels pending lookup work. Re-entering
  confirmation performs a fresh lookup. Draft fields survive lookup failures.
- Offline/server/quota/configuration errors include recovery guidance. Explicit
  retry is available after a failure or invalid result. Requests time out after
  25 seconds. Backend retries remain governed by server configuration.
- The one final **Confirm and add order** action confirms the selected location
  and receipt details; no extra verification switches or accept screen were
  introduced. Phase 6 still requires meaningful correction of uncertain OCR
  fields and prevents duplicate orders/receipts.

## Data boundary and remaining work

Saved client orders carry the original editable text, the selected coordinates,
and a separately preserved unit in `address`. They carry the reviewed candidate,
including its Place ID and normalized label, in a client-only `addressReview`
record. The orders list and marker description show that selected label and unit,
rather than presenting a conflicting input address as the chosen destination.
The original input remains unchanged for receipt fingerprints and audit context.

The existing route API serializes only its supported address contract. It does
not send the client review record as trusted validation. During this migration,
the editable address is still the backend lookup input; Google-generated names
such as 'City Hall' are not substituted into receipt-format validation. No fake
backend reference or `validated_location` is generated by the client.

Order/review data remains in memory, as before. Step 4 will implement persistence
and server-issued confirmation references. Step 5 will route using Place IDs.
Consequently, selecting an ambiguous or review-required address in this UI does
not yet make the existing optimizer consume that selection: optimization can
still reject it when it independently revalidates the original text. This is
not an end-to-end validation-complete release.

## Manual testing needed — Android emulator

Keep the Google-backed backend running on port 8002. For the standard Android
emulator, the mobile `.env` should use `EXPO_PUBLIC_API_URL=http://10.0.2.2:8002`
(the emulator's route to the host). Retain any working existing port-forwarding
setup instead if already configured. Restart Metro after changing environment
configuration. Use the existing native development app that supports ML Kit;
no native dependency changed, so this step itself requires no APK rebuild.
Never copy the server's Google key into the mobile environment.

From `mobile/`, start Metro with `npm start -- --clear`, then open/reload the
existing Android app. Use a mock receipt and edit its delivery address to avoid
needing a new photo. Each pause in address editing may use another lookup.

Google may not return several usable candidates for a chosen live address.
Multiple-candidate behavior is covered deterministically by controller tests;
do not infer a failure solely from a live query returning one candidate. Exact
entrance quality, physical-phone camera behavior, and Apple Maps behavior are
outside this emulator walkthrough.

## Follow-up: time and address display

The confirmation form now shows only the placed clock time in Eastern Time
(`America/New_York`), using AM/PM and automatic EST/EDT daylight-saving behavior.
The complete ISO timestamp remains internal for age calculations and receipt
fingerprints. Editing time retains the original Eastern calendar date; a missing
receipt time uses the current Eastern date. Invalid clock values and nonexistent
spring-forward times block saving. The repeated fall-back hour retains the
original timestamp's offset when available. Re-entering an unchanged displayed
time preserves seconds and does not falsely resolve an uncertain OCR time.

The candidate card shows the normalized full address once; the extra repeated
city/state/ZIP line was removed. Warnings and unit information remain visible.

The mobile suite now has 104 passing tests, including seven timezone/editing
regressions. Manual check: reload the app, verify no date or ISO text appears in
the placed-time input, change it to `3:15 PM`, and confirm the edited time remains
after leaving the field. Invalid input such as `25:00` must disable confirmation.
Check that the selected address card displays its town/state/ZIP only once.
